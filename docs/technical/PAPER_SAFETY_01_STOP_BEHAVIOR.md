## 1. 요약

1. PAPER에는 서버 상태 머신이 사실상 없다. 엔진 상태는 `running`(실행 중 여부)과 `emergency_stopped`(표시용 플래그) 두 불리언뿐이다. `engine.py:91-92`
2. UI의 **"자동매매 일시정지"**(`POST /strategy/stop`)와 **"긴급 중지"**(`POST /strategy/emergency-stop`)는 같은 `engine.stop()`을 호출한다. 차이는 `emergency_stopped` 플래그와 저널 기록의 `emergency` 값뿐이며 차단 범위는 같다. `api/paper.py:158-169`, `engine.py:185-203`
3. 정지하면 **새 매수·매도 판단뿐 아니라 보유분의 손절·익절·최대 보유일·이동평균 청산 감시도 모두 멈춘다.** 이 감시는 실행 루프 안에서만 돌기 때문이다. 보유 주식은 그대로 남고 보호되지 않는다. `engine.py:290`, `trading/exits.py:28-85`
4. 정지는 **전량 청산이 아니다.** 어떤 정지 경로에도 매도 호출이 없다. 포지션·현금은 유지된다.
5. 정지는 **수동 모의 주문(`POST /orders`)을 막지 않는다.** 긴급 중지 후에도 같은 계정의 수동 모의 주문은 접수된다. `api/paper.py:116-125`
6. 서버 재시작 후 엔진은 항상 정지 상태이며 자동 재개되지 않는다. 반면 정지 사유(긴급 여부)·당일 주문 횟수·재매수 대기 등 엔진 메모리 값은 저장되지 않는다.

## 3. 상태 머신 (실제로 존재하는 것)

[사실] 명시적 상태 열거형이나 전이 검사는 없다. 상태는 두 불리언의 조합이다.

| `running` | `emergency_stopped` | UI 표시 | 만드는 경로 |
|---|---|---|---|
| False | False | 정지됨 / 전략 정지 | 초기, 일시정지, 재시작 직후, 실행 오류 종료 |
| True | False | 실행 중 | `start()` (`engine.py:167-183`) |
| False | True | 긴급 정지 | `stop(emergency=True)` |
| True | True | 정상 흐름에서는 없음. 표시 코드에 "긴급 정지 표시와 실행 표시" 불일치를 다루는 문구가 PR #5에 있음(미검토) | — |

표시 로직: `app.js:18`(`긴급 정지`→`실행 중`→`정지됨` 순), `app.js:130`.

세부 사실:

- `start()`는 이미 실행 중이면 `False`를 반환하고 아무것도 하지 않는다. 시작 시 `emergency_stopped=False`로 지우고 판단 이력(이동평균 이력·직전 추세·진입 대기·확인 횟수)을 초기화한다. `engine.py:167-179`
- `stop()`은 호출할 때마다 `emergency_stopped`를 인자값으로 **덮어쓴다.** 따라서
  - 이미 정지된 엔진에 긴급 중지를 누르면 `emergency_stopped=True`가 되고, 화면은 "긴급 정지"가 된다(실제로 막은 것은 없음). `engine.py:185-188`, `app.js:207`(긴급 버튼은 항상 활성)
  - 긴급 정지 후 전략 선택·로그아웃·초기화·자산 복사가 일어나면 내부 `stop()`(emergency 기본 False)이 플래그를 지워 "정지됨"으로 바뀐다. `services/paper_workspace_service.py:86,120`, `api/auth.py:103`, `api/paper.py:110`
- `STRATEGY_STOP` 저널은 `was_running`일 때만 기록된다. 정지 상태에서 누른 긴급 중지는 저널에 남지 않는다. `engine.py:196-202`
- 실행 루프가 예외로 끝나면 `running=False`, 메시지 "실행 오류로 중지됨"만 설정되고 `STRATEGY_STOP` 저널과 `emergency_stopped`는 설정되지 않는다. `engine.py:215-219`

### 4.3 정지 시점에 진행 중인 작업

- [사실] 매수·매도·청산 한 번(`step()`)은 `await` 없는 동기 코드다. 같은 이벤트 루프에서 정지 요청이 그 중간에 끼어들 수 없으므로, 한 번의 `step()` 안에서 주문이 반쯤 처리된 채 취소되는 경로는 코드상 없다. `engine.py:283-390`
- [사실] 정지 요청은 이벤트 루프의 `step()`이 끝난 뒤에야 처리된다. `_sell()`은 최대 1,000주씩 반복해 보유분 전체를 청산하는 루프이므로(`engine.py:471-488`) 이미 청산이 시작된 `step()`은 정지 요청과 무관하게 끝까지 완료된다.
- [사실] PAPER 주문은 즉시 `FILLED` 또는 `REJECTED`로 끝나며 대기·미체결 상태가 없다(`models.py:16-18`, `paper.py:303-335`). 따라서 정지 시 **취소할 미체결 주문이 없다.** 정지 후에 되돌려지는(취소되는) 체결도 없다. 이미 체결된 모의 주문은 정지해도 그대로 남는다.
- [사실] 수동 주문 엔드포인트는 일반 `def`라서 스레드풀에서 실행된다. `PaperBroker.submit`은 `RLock`과 `@persisted`로 직렬화된다. `paper.py:18-46`, `:285-287`. 정지 요청과 동시에 들어온 수동 주문은 허용된다.
- [가설] 정지 요청은 같은 계정 락(`_serialize_paper_change`)을 기다린다. 다른 변경 작업이 락을 쥐고 있으면 정지가 그만큼 늦는다(5절 R4).

### 4.4 주문 직전 방어

[사실] `broker.submit()` 안에는 엔진 `running` 검사가 없다. 방어는 호출하는 쪽에 있다.

- 자동 매수: `_can_order()`(운영 시간·재매수 대기), 하루 주문 한도, 수량 1 이상, 위험 한도 `check_buy`(투자금·현금 비율·일 손익·주문 횟수), 현금 부족 `engine.py:427-459`, `paper.py:304-311`
- 자동 매도: `_within_hours()` 하나뿐. 위험 한도 검사는 매수에만 있다. `engine.py:461-465`, `paper.py:304-307`
- 어느 것도 "사용자가 정지를 눌렀는가"를 확인하지 않는다. 정지가 루프 취소에 의존하며 주문 직전에 별도로 정지 플래그를 검사하지 않는다는 것이 코드상 사실이다. 이 검사가 불필요하다는 설계 의도나 충분한 안전성은 확인하지 않았다. 수동 주문 경로에도 정지 상태 검사가 없다(4.2).

## 6. 재시작과 저장값 복구

[사실] 서버 시작 시 어떤 코드도 `engine.start()`를 호출하지 않는다. `start`의 호출 위치는 `api/paper.py:154` 하나다(`engine.start` 검색 결과). 재시작 후 엔진은 `running=False, emergency_stopped=False`다.

복구 흐름:

1. `lifecycle.py:53-58`: `broker.initialize()` → 저장된 상태 복구 → `_restore_paper_strategy`.
2. `paper.py:148-173`: 현금·보유·주문·`auto_lots`·관리 범위 복구. 소유 lot과 청산 규칙은 유지("Execution remains stopped"). `_managed_lots`는 비우고 `_strategy_positions`도 비운다.
3. `runtime.py:208-217`: 마지막 선택 전략이 저장되어 있고 DRY_RUN이면 `configure()`로 다시 적용 → `reset_performance_baseline()` → `begin_strategy()`가 `auto_lots`에서 관리 lot을 재구성한다(`engine.py:625`, `:556-570`, `paper.py:225-254`).
4. 사용자가 다시 "전략 시작"을 눌러야 감시가 재개된다. 시작에는 저장된 스냅샷과 선택 전략이 필요하다. `api/paper.py:150-153`

주의(사실): `begin_strategy`는 `run_id`를 새로 만들고 `@persisted`로 상태를 저장한다. 즉 재시작·전략 재선택마다 기준 손익이 다시 잡힌다(`paper.py:250`). 사용자 확인 없이 성과 기준이 바뀌는지는 이번에 판단하지 않았다(미검증).

[미검증] 실제 재시작 후 `auto_lots`가 모든 보유분을 정확히 복구하는지, `unassigned` 보유분이 감시 대상에서 빠지는지(`paper.py:206-212`는 관리되지 않는 수량을 `managed=False`로 표시함)는 실행·데이터 확인이 필요하다.

### 6.1 같은 프로세스의 stop/start와 서버 재시작 구분

- [사실] 같은 엔진 객체의 `stop()`은 `last_data_at`, `last_decision_at`, `data_message`, `_signals`를 초기화하지 않는다. 이어지는 `start()`는 `tick_count`, 이동평균 이력, snapshots 등은 초기화하지만 위 네 항목은 지우지 않는다. `engine.py:167-203`
- [사실] `status()`는 남은 시각·메시지·최근 신호를 그대로 반환한다. `checked_at`은 조회 시각이므로 새 시세나 새 판단의 발생을 증명하지 않는다. `engine.py:636-671`
- [가설] 별도 설정 변경 없이 정지 후 다시 시작하면 첫 새 시세/판단 이전에 `running=True`, 초기 tick/snapshots와 이전 실행의 시각·메시지·신호가 함께 보일 수 있다. 실제 화면·타이밍은 미검증이다.
- [사실] 관리 범위 변경이나 전략 `configure()`는 시각·메시지를 별도로 초기화한다(`engine.py:537-543,617-619`). 성과 기준 초기화는 신호 이력을 지운다(`engine.py:556-570`). 따라서 모든 재시작 경로에 같은 잔여 상태가 남는다고 일반화할 수 없다.
- [사실] 서버 프로세스 재시작으로 새 엔진이 만들어지면 생성자에서 시각은 `None`, 메시지는 시세 수신 대기, 신호는 빈 목록이다(`engine.py:77-100`). 이후 저장 전략 복구와 configure는 6절의 별도 경로다. 실제 복구 정확성은 미검증이다.
- [사실] 상태 조회 `strategy_status`는 일반 `def`이며 변경 API에 쓰는 `_serialize_paper_change`가 붙어 있지 않고, `status()`도 두 불리언과 다른 필드를 하나의 락 아래 읽지 않는다. `api/paper.py:128-130,147-169`, `runtime.py:176-181`, `engine.py:636-671`
- [가설] 동시 상태 조회가 상태 변경 중간 값을 읽어 필드 조합을 섞을 가능성이 있다. 특정 조합(예: `running=True`와 `emergency_stopped=True`)의 발생이나 빈도는 재현하지 않았으며 이번 분석으로 확정하지 않는다.

## 7. 정지 ≠ 전량 청산

| 조치 | 코드가 하는 일 | 하지 않는 일 |
|---|---|---|
| 일시정지 | 루프 종료, 감시·자동 주문 중단 | 매도, 주문 취소(취소할 것 없음), 손절 대행 |
| 긴급 중지 | 위와 동일 + 표시 플래그 | **매도·청산 없음.** 일시정지보다 더 막는 것 없음 |
| 모의 초기화 `DELETE /paper/reset` | 정지 후 계좌를 초기 기준으로 되돌림 | (청산이 아니라 데이터 초기화) `api/paper.py:107-113` |

전량 청산 기능은 조사한 PAPER 코드에 없다. 사용자가 보유분을 정리하려면 수동 모의 주문을 써야 한다(`api/paper.py:116`). 이 문서는 청산 기능을 제안·구현하지 않는다.

**긴급 중지 버튼 옆 안내**

> 이 계좌의 자동매매를 멈춥니다. 보유 주식을 팔지 않으며, 일시정지와 같이 손절·익절 감시도 함께 멈춥니다. 다른 모의계좌의 전략과 직접 낸 모의 주문은 멈추지 않습니다.

**긴급 정지 상태 배너**

> 긴급 정지됨 · 자동 주문과 보유분 감시가 꺼져 있습니다. 보유 주식은 그대로입니다. 다시 시작하기 전까지 손절이 작동하지 않습니다.

**정지 완료 메시지**

> 자동매매를 멈췄습니다. 보유 주식은 유지되며 감시는 다시 시작할 때까지 꺼져 있습니다.

**서버 재시작 후 안내**

> 서버가 다시 시작되어 자동매매는 정지 상태입니다. 저장된 보유 내역과 감시 대상이 맞는지 확인하세요. 오늘 주문 횟수와 재매수 대기 기록은 이어지지 않을 수 있습니다. 전략 시작을 눌러야 감시가 재개됩니다.

**"전량 청산"과 혼동 방지 문구**

> 정지는 매도가 아닙니다. 보유 주식을 정리하려면 직접 모의 매도 주문을 내세요.
