# FOLIO AI 협업 운영 절차

적용 규칙: [AGENTS.md](../../AGENTS.md)의 `FOLIO-COLLAB-1.2`. 공통 규칙을 실행하기 위한 절차이며 금융·운영 보호 정책을 대체하거나 완화하지 않는다. Claude Code도 [CLAUDE.md](../../CLAUDE.md)를 통해 같은 규칙을 따른다.

## 문서의 역할과 현재 상태

- 공통 의무와 권한은 AGENTS.md, 상세 절차는 이 문서, 작업별 범위와 결과는 개별 작업 기록에 둔다. 상세 사양을 반복 복사하지 않는다.
- [기존 문서 관리 기준](../README.md)에 따라 기술 절차는 `technical/`, 작업 계획·승인·진행 기록은 `plans/ai-tasks/`에 둔다. 기존 제품 상태·로드맵·과거 이력을 대체하지 않는다.
- 구현된 것은 문서와 템플릿이다. 자동 파일 잠금, 사전 검사 스크립트, GitHub Actions는 아직 없다. 체크리스트 작성이나 PR 생성 자체가 안전 검사를 강제하거나 승인 사실을 만들어 주지 않는다.

## 작업 기록과 승인

1. 작업 ID는 `YYYYMMDD-담당AI-주제`처럼 정하고 기존 기록과 열린 PR을 검색해 중복을 피한다. 중복이면 식별 접미사를 붙인다.
2. [TEMPLATE.md](../plans/ai-tasks/TEMPLATE.md)를 바탕으로 `docs/plans/ai-tasks/<작업-ID>.md`를 만든다. 작업 기록 파일도 허용 파일에 명시하고 PR에서 연결한다. TEMPLATE.md 자체에 개별 작업을 누적하지 않는다.
3. 담당 AI, 브랜치, Worktree 절대 경로, 기준 커밋 전체 SHA, 수정 허용 파일, 선행 작업, 완료 조건, 검증 범위와 승인 상태를 채운다. 선행 작업이 없으면 `없음`으로 기록한다.
4. 검증 범위에는 승인된 정확한 명령, 환경 분리 확인, 미실행·금지 항목을 적는다. 명령 예시는 실행 승인이 아니다. 승인 근거는 사용자 지시의 요약과 참조로 남기며 비밀정보를 복사하지 않는다.
5. 승인 상태(`제안 / 승인 / 추가 승인 필요`)와 진행 상태(`대기 / 작업 중 / 검토 대기 / 통합 완료 / 중단`)를 별도로 관리한다. 승인 범위를 벗어나면 상태와 범위를 갱신하고 필요한 승인을 받은 뒤 재개한다.
6. 인계할 때 선행 commit·PR, 남은 일, 공통 파일 담당자와 다음 담당자의 허용 범위를 기록한다. main 병합 전에는 통합 완료로 표시하지 않는다.

이번 v1.2 도입 작업은 사용자 허용 파일이 다섯 문서로 제한되어 있으므로 작업 기록을 기존 PR #1 본문에 남긴다. 이후 작업부터는 독립 작업 기록 파일을 사용한다. 이 예외는 이후 작업의 파일 범위를 임의로 넓힐 근거가 아니다.

## 착수와 동시 작업 확인

- 현재 브랜치, Worktree, HEAD, 원격 주소 및 staged·unstaged·미추적 파일 목록을 확인한다. 다른 작업자의 변경을 수정·삭제·임의 staging하지 않는다.
- GitHub의 원격 작업 브랜치와 열린 PR(Draft 포함)을 확인한다. 다른 작업의 PR 변경 파일과 작업 기록의 수정 예정 파일까지 대조한다. PR 없는 작업 브랜치도 확인 대상이다.
- 활성 여부나 담당 범위를 확인할 수 없거나 중복 수정 가능성이 있으면 중단하고 보고한다. 공통 파일은 담당자와 순서를 합의한 후 재개한다.
- 독립 파일·Worktree는 실시간 잠금이 아니다. 조회 직후 새 작업이 시작될 수도 있고 로컬 전용 작업은 GitHub에 보이지 않을 수 있다. 범위 변경·인계 및 commit·push 직전에도 관련 상태를 다시 확인한다.

## Commit·Push 안전 절차

아래 명령은 승인된 작업에서 수행할 점검 예시다. 앱 시작, 테스트 실행, 인증정보 열람 권한을 부여하지 않는다.

1. **대상 확인:** `git branch --show-current`, `git rev-parse --show-toplevel`, `git worktree list --porcelain`, `git rev-parse HEAD`로 작업 기록과 대조한다. 원격 저장소와 push 대상 브랜치를 확인한다. 원격 URL에 인증정보가 포함될 가능성이 있으면 원문을 출력하지 않는다.
2. **파일 범위 확인:** `git status --short`, `git diff --name-status`, `git diff --cached --name-status`로 미추적·수정·삭제·이름 변경과 기존 staging을 확인한다. 작업 시작 상태와 허용 파일 목록을 대조한다. 예상 밖 변경을 임의 복구하거나 가져오지 않는다.
3. **민감 경로 우선 확인:** 파일명과 경로에서 `.env`, 로컬 비밀정보 디렉터리, 키·인증서, 계좌자료, DB 덤프, RAW 운영 데이터, 개인 기록, 백업·실행 산출물을 식별한다. `.gitignore`만으로 이미 추적된 자료까지 보호된다고 가정하지 않는다. 합성 예제도 이름만 보고 허용하지 않고 승인 범위를 확인한다. 의심 파일은 내용을 열지 않고 중단한다.
4. **명시적 staging:** `git add -- <허용 파일 경로...>`처럼 파일을 지정한다. `git add .` 또는 `git add -A`로 다른 변경을 함께 넣지 않는다. 기존 타인 staging이 있거나 소유권이 불명확하면 그대로 두고 중단한다.
5. **커밋 전 검토:** staged 목록과 `git diff --cached`의 전체 변경을 검토하고 `git diff --cached --check`로 공백 오류를 확인한다. 내용 검토는 민감 경로 검사를 통과한 허용 소스·문서에 한한다. 비밀정보 의심 시 추가 출력 없이 중단한다. 승인된 검증만 수행하고 결과·미실행 사유를 남긴 뒤 commit한다.
6. **전송 이력 검토:** 원격 담당 브랜치 SHA를 읽기 전용 조회해 시작 시점과 비교한다. 기존 원격 브랜치라면 해당 SHA가 로컬 이력의 조상인지 확인하고, `<확인한 원격 SHA>..HEAD`의 모든 커밋과 각 커밋의 변경 파일·diff를 검토한다. 최종 diff에서 사라진 민감자료도 중간 커밋에 남을 수 있다. 최초 push라면 승인된 기준 커밋을 원격 기준과 대조하고 `기준 커밋..HEAD` 전체를 확인한다. 기준이 불확실하면 중단한다.
7. **중단과 보고:** 원격 변경, 충돌, 범위 초과, 비밀정보 의심, 검사 실패 또는 확인 불확실은 통과로 처리하지 않는다. 자동 merge·rebase·force push, 검사나 hook 우회로 진행하지 않는다. 실제 비밀값은 로그·보고서·PR에 남기지 않고 발견 단계와 필요한 조치만 보고한다. 비밀정보 열람·수정·이력 정리는 별도 승인 없이 하지 않는다.
8. **일반 push와 사후 확인:** 정상 확인된 origin과 담당 브랜치를 명시해 일반 push한다. 원격 SHA, 로컬 상태, PR head·base와 Draft 상태를 확인한다. 인증·권한 문제는 설정을 임의 변경하지 말고 보고한다. 원격 상태가 검토 후 달라졌다면 강제로 맞추지 않는다.

위 절차는 현재 사람이 확인하는 문서상 정책이다. 자동 사전 검사·비밀정보 탐지 도구는 아직 도입되지 않았으며, 수동 검토가 민감정보 부재를 완전히 보장하지 않는다.

## 완료 보고와 사용자 확인

AGENTS.md의 기존 완료 보고 및 GPT 보고 항목을 유지하고 [PR 양식](../../.github/pull_request_template.md)에 결과를 기록한다.

- 구현 이유와 선택한 방식의 장점·단점·제약을 실제 변경과 연결해 설명한다.
- 구현된 부분과 미연결 부분을 구분한다. 구현, 자동 테스트, 실제 동작 검증, 사용자 확인, 운영 적용 상태를 각각 적는다. 해당 없음은 이유를 적고 완료로 바꾸지 않는다.
- 자동 테스트를 실행했다면 명령·환경·결과·대상 SHA를 기록한다. 실제 동작 검증은 별도 절차·결과로 적는다. 과거 결과를 이번 결과로 재사용하지 않는다.
- 사용자 확인 절차에는 준비 환경, 순서, 예상 결과, 미확인 시 제한을 적는다. 운영 접근이 필요한 절차는 필요한 승인을 명시하고 직접 실행하지 않는다. 사용자 확인 전에는 전체 기능 완료로 표시하지 않는다.
- 이번 변경을 이해하는 데 필요한 개발 개념 1~2개와 미검증 항목·남은 위험·GPT 검토 사항을 적는다. API·DB 계약 변경과 다른 AI와 충돌 가능한 공통 파일도 빠뜨리지 않는다.
- 문서 작업의 직접 확인은 PR의 Files changed에서 범위·규칙·링크·양식을 읽는 것으로 안내할 수 있다. 이것은 애플리케이션 동작 검증이 아니다.

## 향후 자동 검증

사전 검사 도구와 CI 도입은 별도 작업·승인 대상이다. 이 단계에서는 생성하거나 실행하지 않는다. 후보 선정 시 테스트 파일의 import 부작용, DB·네트워크·파일 쓰기·워커 실행 여부까지 읽기 전용으로 조사한다. 테스트 이름이나 mock 일부 사용만으로 안전하다고 판단하지 않는다. 전체 테스트 탐색을 기본 허용하지 않으며 승인된 개별 명령과 격리 환경을 먼저 정한다.
