## 원인별 근거와 판단

### 1. 장 초반 보완 수집이 정규 수집을 대기시킴 — 강한 근거

11월 3일 run 6579(opening_0910)는 09:10:10~09:18:07, 476.889초 걸렸고 26건을 복구했다. 정규 수집 run 6580은 09:19:02에 재개되어 종목 지연 110건을 저장했고, 뒤따른 지수 run 6581은 09:19:46~47에 지연 10건을 저장했다. 이날 첫 정규 수집도 09:05:02여서 09:00 종목 봉 18건이 5분을 약간 초과했다. 첫 실행이 09:05인 이유까지 이 기록만으로 단정하지 않는다.

11월 4일에는 다음 두 작업이 연속 실행됐다.

| run | 종류 | 시작~종료 | 소요 | 신규 복구 | 최종 오류 |
|---|---|---|---:|---:|---|
| 7020 | opening_0905 | 09:06:32~09:11:36 | 304.090초 | 10 | 036930 RATE_LIMIT |
| 7021 | opening_0910 | 09:11:36~09:20:21 | 524.365초 | 115 | 034020 RATE_LIMIT |

이 구간에는 같은 수집 워커의 정규 종목·지수 실행이 없었다. 정규 run 7022는 09:21:02에 재개되어 지연 종목 147건을, 지수 run 7023은 09:22:35에 지연 지수 14건을 저장했다. `_run()`이 정규 수집과 보완 수집을 각각 await하는 구조이고 정규 수집 내부도 종목 뒤에 지수를 순차 수집하므로, 다른 스레드에서 실행하더라도 이 워커의 다음 정규 작업은 보완 수집 완료까지 기다린다. 이 구조와 실행 기록·저장 행의 연결이 일치한다.

`gap_repair.py`는 장 초반에도 최소 count=600을 요청하고, `market_data.py`는 페이지당 최대 200개로 최대 3페이지를 처리한다. 부족한 몇 개 봉을 보완할 때도 넓은 이력 조회가 발생할 수 있다. 실제 각 HTTP 페이지 수와 응답 지연은 수집 실행 테이블에 남지 않아 정확한 요청 수는 확정하지 않았다.

### 2. RATE_LIMIT과 제한적 재시도가 장 초반 소요를 더 늘림 — 부분적으로 확인

11월 4일 RATE_LIMIT 4건 중 2건은 위 보완 작업, 2건은 정규 run 7032(09:30:02~09:32:24, 105560)와 7034(09:33:02~09:34:29, 005930)에서 발생했다. 005930의 09:30 봉은 7034에서 최종 오류가 난 뒤 7036에서 09:35:17에 처음 저장되어 해당 1건의 지연과 직접 연결된다. 105560 실패가 같은 봉의 5분 초과로 이어졌다고 단정할 근거는 없다.

조회 전송 코드는 GET에 한하여 최대 3회 시도하고, 429의 Retry-After/리셋 대기 및 그룹별 직렬화·간격을 적용한다. 재시도 대기 판단에는 20초 deadline이 있으나 전체 보완 작업 시간을 20초로 제한하는 장치는 아니다. 여러 대상·페이지를 순차 처리하므로 전체 작업은 분 단위가 될 수 있다.

품질 보고서의 error_counts는 최종 실패 대상 항목 수다. HTTP 요청 횟수나 재시도 횟수가 아니며, 성공으로 끝난 일시적 429/timeout은 여기에 남지 않을 수 있다. 따라서 보완 수집의 828.455초 중 정확히 몇 초가 재시도·응답 대기·락 대기인지 현재 영속 기록으로 분해할 수 없다. RATE_LIMIT 총수가 감소했는데도 지연이 증가한 것은 모순이 아니다.

## 다음 조치 제안 — 이번에는 구현하지 않음

1. 정규 수집 우선권을 보장하고 보완 작업에 시간·페이지 예산을 둔다. 장 초반은 필요한 짧은 구간만 보완하고 작업을 나누어 정규 주기 사이에 양보하도록 설계한다. 무제한 병렬화로 429를 악화시키지 않으며 최종 공급자 전체 구간 검증은 유지한다.
2. 종목·지수 공통 요청 예산을 검토하고 요청별 attempt, group, HTTP 상태, Retry-After, 응답/락/재시도 대기시간, worker 예정/실제 시작 차이를 비밀정보 없이 계측한다. 현재 기록만으로는 재시도 기여 시간을 확정할 수 없다.
3. 미국 직접 지표 TIMEOUT은 별도 원천 연결 상태로 추적한다. 대용 지표 확보와 국내 봉 완전성 판정에 혼합하지 않는다.
4. 변경 후 관찰 기준은 장 초반 정규 수집 공백, 5분 초과 비중, 보완 실행 소요·429 빈도다. 학습·전략 변경 대신 수집 지연 개선 여부를 확인한다.

## 예약 수정 가능 여부와 필요한 조치

**현재는 적용 보류**다. 기존 오후 5시 예약과 프롬프트는 변경하지 않았고 automation.toml SHA-256이 이전 기준 `762912ff8433bc313718454d49b35205b2bd8a22024ec858f0fd260eeea28b5a`와 같음을 다시 확인했다.
