# 장 초반 정규 수집 우선 처리

근거: `docs/ml-followup-2026-11-04.md`, 기준 커밋 `75f3cf4ca292b2b0234fffc2c34ccee6be4ed494`.

## 변경 동작

정규 수집과 보완 수집은 계속 한 워커에서 순차 실행한다. 보완 작업을 병렬로 늘리지 않는다. 09:05·09:10 보완은 짧은 조각으로 실행하고, 두 보완 작업을 합쳐 정규 수집 간격당 한 조각만 허용한다. 같은 예정 시각이면 정규 수집이 먼저 실행되고, 두 보완 작업은 번갈아 처리된다.

- 조각별 예산: 최대 **5초, 논리적 차트 페이지 2개**. 다음 정규 수집까지 1초 여유를 남기도록 시간 예산을 더 줄인다. 여유가 없으면 조회하지 않고 다음 주기로 넘긴다.
- 차트 페이지당 기존 GET 재시도 최대 3회와 그룹별 요청 간격·429 cooldown은 유지한다. 재시도·요청 간격 대기가 남은 예산에 들어가지 않으면 양보한다. 간격을 줄이거나 cooldown을 우회하지 않는다. 2페이지는 재시도 포함 HTTP 시도 2회라는 뜻이 아니다.
- 유지보수 호출에만 ContextVar 예산을 적용한다. 네트워크 소켓 타임아웃과 그룹/종목/토큰 락 대기도 남은 시간에 제한한다. 일반 정규 수집과 주문 호출의 기본 정책은 바꾸지 않는다.
- 장 초반은 해당 보완 시각의 완료 봉 격자를 고정한다(09:05는 5분, 09:10은 10분). 최초 누락 구간 주변을 한 페이지로 조회하며 `before`와 한 봉 여유를 사용한다. 기존 최소 600개 조회는 장 초반 예산 경로에서 사용하지 않는다. 주식 API의 작은 count도 실제 요청에 전달한다.
- 처리한 응답은 수신 시각으로 append-only 저장한 뒤 양보한다. 미처리 대상·일시 실패 대상·격자 시각은 실행의 `_diagnostics.resume`에 기록한다. 다음 정규 주기 이후 이 커서로 이어서 처리한다. 다시 시작해도 DB에서 이미 저장된 봉을 확인하고 기존 ON CONFLICT DO NOTHING을 사용하므로 재기록하지 않는다.
- 시작 시 당일 마지막 커서를 읽어 09:12 이후에도 진행 중 작업을 재개한다. 갑작스러운 중단으로 마지막 커서가 이전 위치를 가리켜도 저장된 데이터 재확인으로 안전하게 재방문한다. DB 커서 복원이 실패하면 경고를 남기며 장 마감 검증은 유지한다.
- 15:31 이후 장 초반 조각은 실행하지 않는다. 15:35 최종 보완과 15:40 품질 워커의 전체 검증은 기존 경로·조회 범위·391분 격자·공급자 부재 판정을 유지한다. 수집 누락/지연의 품질 기준도 변경하지 않는다.

예산 소진 자체는 원천 오류로 집계하지 않고 조각 완료와 남은 커서를 구분한다. 실제 TIMEOUT·429로 재시도를 양보한 경우 마지막 오류 분류는 유지한다. DB의 COMPLETED는 그 조각의 오류 없음이며, 전체 보완 작업 완료 여부는 `resume`이 null인지로 확인한다.

## 검증 결과

- 수집·품질·원본 저장·매크로·Toss·과거 봉·시장 시간·아키텍처 회귀 테스트 12개 모듈: **117개 통과**.
- JavaScript 회귀 테스트: **22개 통과**.
- 결정적 시뮬레이션: 보완 조각이 매번 예산을 다 사용하는 동안 정규 수집은 09:05:02, 09:06:02, 09:07:02에 실행되어 시작 간격 60초·스케줄 지연 0초였다.
- 작은 주식 누락 조회: 10분 격자에 11개(커서 한 봉 여유)를 요청하고 실제 차트 호출이 한 페이지였음을 검증했다. 이전 600개 조회는 페이지 상한이 3개였다. 실서비스의 과거 실제 페이지 수는 기록이 없어 비교 수치로 단정하지 않는다.
- 격리 PostgreSQL 스키마 테스트에서 페이지 예산 중단→커서 복원→나머지 대상 저장→동일 커서 재실행 시 신규 저장 0건을 확인했다. 기존 행의 available_at도 유지됐다.
- 장 마감 전체 보완, 공급자 부재와 미검증 구분, 수신 시각/미래 데이터 접근 제한, 429·TIMEOUT·5xx 재시도, 실패 후 복구가 회귀 테스트를 통과했다.

로그는 Git 제외 경로 `artifacts/ml/generated/collection-priority-validation/python-tests.log`, `js-tests.log`에 있다. 기존 전체 테스트 중 학습을 수행하는 환경/실험 테스트와 백테스트 실행 테스트는 이번 안전 범위에 따라 실행하지 않았다. 실제 품질검사·수집·백테스트 명령도 실행하지 않았다.

## 남은 위험 및 운영 적용

실시간 장중 검증은 수행하지 않았다. 실행 중 서버·DB를 재시작하거나 핫 리로드하지 않았으므로 현재 서비스에 새 코드가 적용됐다고 보고하지 않는다. 다음 승인된 배포·시작 절차에서 반영해야 한다. Strategy ID 17, DRY_RUN, 계좌·주문, 모델, 오후 5시 예약, Drive 관련 파일과 인증은 변경하지 않았다.

5초는 요청 시작·대기·락·소켓에 적용하는 **협력적 예산**이며 운영체제 수준의 강제 중단 보장은 아니다. DNS/소켓의 세부 동작, 여러 번 나누어 들어오는 응답, DB 조회·저장·실행 마감 기록이 예산을 초과할 수 있다. 기존 정규 수집 자체가 1분 넘게 걸리는 문제도 이 변경으로 자동 해결되지 않는다. 그 경우 다음 수집 경계에 여유가 없으면 보완을 계속 양보하며 최종 검증으로 넘어갈 수 있다.

프로세스가 실행 중단 시점에 커서를 아직 저장하지 못했으면 마지막 커서 위치부터 안전하게 재방문한다. 커서 없는 최초 조각이 09:12 이후 중단/재시작됐거나 DB 커서 복원이 실패한 경우 장 초반 재개 대신 장 마감 전체 보완에 의존할 수 있다. 이는 원본을 잃는 동작이 아니지만 장중 복구가 늦어질 수 있다.

## 다음 거래일 확인 항목

1. 다음 국내 증시 거래일에 배포 버전이 실행 중인지 확인한다. 09:01~09:30의 정규 실행 간격과 `regular_interval_seconds`, `regular_schedule_lag_seconds`를 관찰한다. 휴장 여부는 실제 거래일 기준으로 판단한다.
2. opening 실행의 `_diagnostics.budget`에서 max_seconds, elapsed_seconds, pages/max_pages, socket_requests, wait_seconds, pending_targets, reason을 비교한다. 두 보완 작업이 같은 정규 주기 사이에서 연속 독점하지 않는지 확인한다.
3. resume의 대상 수가 줄고, 중단된 대상이 나중에 처리되는지 확인한다. 429·TIMEOUT과 예산 양보를 구분하고 인증/계좌값은 기록하지 않는다.
4. 11월 4일 기준(종목 241·지수 24건, 보완 125건·그중 지연 103건, 장 초반 연속 보완 828.455초)과 비교한다. 시장/공급자 조건이 달라질 수 있으므로 지연 감소를 미리 보장하지 않는다.
5. 장 마감 최종 공급자 근거, 원시 미확보·PROVIDER_ABSENT·COLLECTION_GAP·UNVERIFIED, 실제 수집 누락을 확인한다. 보완을 줄여 최종 완전성이 나빠지지 않았는지 확인한다.
